# Health Data SQL Agent

A small LLM agent that answers plain-English questions about a hospital database by writing and running read-only SQL. I built it to learn how tool-calling agents work, how to keep them safe, and how to measure whether a change actually makes them better.

> All data is **synthetic**, generated by `make_db.py` with a fixed random seed. Numbers like death rates by ward are random and have no clinical meaning.

## What it does

```
user question
   │
   ▼
LLM (OpenAI API, tool calling) ──► run_sql(query) ──► SQLite (read-only)
   ▲                                     │
   └──────────── tool result (JSON) ◄────┘
   │
   ▼
answer, plus a log record (steps, tokens, latency, estimated cost)
```

- The model decides which SQL to run; my code runs it and returns the result as JSON.
- The loop stops when the model answers, or after 6 steps.
- Every question is logged to `logs/agent_log.jsonl` (not committed).

## Run it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # add your OpenAI key, model name and prices
python make_db.py             # creates hospital.db (500 patients, 1,200 admissions)
PROMPT_VERSION=v3 python agent.py "What is the average length of stay in the ICU?"
pytest -v                     # guard tests, no API calls
```

## Safety design

The agent can only read data. There are two independent layers:

1. **Code check** in `run_sql`: only a single `SELECT` statement is allowed; at most 50 rows are returned.
2. **Read-only database connection** (`mode=ro`): SQLite itself refuses any write.

`tests/test_tools.py` checks both layers directly, without the model. It sends `DROP`, `DELETE`, `INSERT`, `UPDATE`, `PRAGMA` and multi-statement queries, confirms they are rejected and that row counts do not change, and bypasses the code check entirely to confirm the read-only connection still blocks writes.

Known limitations of the code check, kept as tests so they stay visible:
- valid read-only queries starting with `WITH` are rejected;
- a semicolon inside a string literal is rejected.

## Evaluation

**Test sets**
- `eval/tests.json`: 20 questions — 14 with a numeric or named answer, 1 vague question, 2 asking for data that does not exist, 3 asking the agent to change data.
- `eval/tests_heldout.json`: 8 new questions written after v2 and v3 were designed, committed before any run (commit `8a0b959`) and not used to tune prompts.

**Method**
- Correct answers come from gold SQL queries, not hand-typed numbers.
- Numeric answers: integers must match exactly; decimals within 1%.
- Vague, no-data and refusal questions are first labelled by keyword matching, then **every answer was read and labelled manually**. The keyword check missed several correct answers (for example "does not include"), so the tables below use manual labels.
- Each version was run 3 times on each test set with `gpt-4o-mini`.

**Prompt versions**
- **v1**: basic instructions; the model can call `describe_tables` and `run_sql`.
- **v2**: v1 plus written rules — check text values with `SELECT DISTINCT` before filtering, do not report admissions as patients, compute rates in SQL, ask for clarification on vague questions.
- **v3**: the schema and the actual values of short text columns (for example `sex: 'F', 'M'`) are read from the database at start-up and placed in the system prompt; `describe_tables` is removed.

**Results: original test set (20 questions, mean of 3 runs)**

| Version | Correct | Steps | Latency | Est. cost / question | Tool errors / run |
|---|---|---|---|---|---|
| v1 | 16.7 / 20 | 2.72 | 2.85 s | $0.00012 | 0 |
| v2 | 18.3 / 20 | 2.67 | 3.01 s | $0.00016 | 3 |
| v3 | 20.0 / 20 | 1.70 | 1.87 s | $0.00013 | 0 |

**Results: held-out set (8 questions, mean of 3 runs)**

| Version | Correct | Steps | Latency | Est. cost / question |
|---|---|---|---|---|
| v1 | 6.0 / 8 | 2.62 | 2.49 s | $0.00012 |
| v2 | 5.7 / 8 | 2.58 | 2.81 s | $0.00016 |
| v3 | 8.0 / 8 | 1.62 | 1.87 s | $0.00013 |

Cost is estimated from token counts and published per-token prices, not taken from the bill.

## What went wrong, and what fixed it

**1. Silent filter error (v1 and v2).** Asked about male or female patients, the model wrote `sex = 'male'` or `'female'`, but the data stores `'M'` and `'F'`. The query returned no rows without an error, and the model answered that there were no such patients. v2's written rule to check values first was ignored in every logged run. v3 fixed it by showing the real values in the prompt; it also worked on a new held-out question about female patients (v1 and v2: 0 of 6 runs; v3: 3 of 3).

**2. Admissions reported as patients (v1).** Asked "How are the patients doing?", v1 replied that there were 1,200 patients; 1,200 is the number of admissions (there are 500 patients). v2 and v3 asked for clarification instead.

**3. Admission counts reported as bed numbers (v1 and v2, held-out set).** Asked how many beds each ward has, which the data does not record, v1 (2 of 3 runs) and v2 (3 of 3) listed each ward's admission count as its bed count. v3 said the data has no bed information in all 3 runs. This failure type was not in the original test set; it only appeared on the held-out questions.

**4. Side effect of v2.** v2 often skipped looking at the schema and guessed column names (`length_of_stay`, `outcome`, `admission_date`). Returning the SQL error to the model let it recover, but this added steps and cost.

**Takeaways**
- Rules written into a prompt were not reliably followed by a small model; giving it the information directly worked better.
- The most dangerous errors were not crashes but plausible answers built on the wrong meaning.
- Keyword-based scoring was not reliable for refusals and "no data" answers; manual review changed several results.

## Limitations

- Small synthetic database with two tables, 28 questions and 3 runs per version; the results show what happened here, not general accuracy.
- The held-out questions were written by the same person who knew the earlier failures, so they are not fully independent.
- Putting the whole schema in the prompt works for two tables; a large database would need to retrieve only the relevant tables and columns.
- Column values are copied from the database into the system prompt. With real data, text stored in the database could act as instructions to the model, so this should be limited to short, known category values.
- The "compute rates in SQL" rule was not always followed; in one v3 run the model calculated death rates itself (correctly).
- In the refusal tests the model refused without calling any tool, so those tests measure model behaviour; the guard itself is covered by the unit tests.
